Inventário data--copilot-guidelines
vs SpecKit Plugin

Auditoria item-a-item dos artefatos do repositório corporativo data--copilot-guidelines em relação aos guardrails, gates e personas do plugin SpecKit. A premissa é inegociável: o plugin é a fonte da verdade, princípios universais vivem apenas em speckit-baseline, e eficiência de tokens é critério de aceite — duplicação textual é desperdício. Esta análise classifica cada artefato em conflito, sobreposição, incoerência interna ou complemento aceitável, e quantifica o impacto de uma adoção crua do build corporativo no contexto carregado pelo Copilot.

Quatro categorias, uma conclusão

Dos 17 arquivos de instructions, 1 skill e 1 agent presentes no repositório corporativo, somente ~8 itens — todos parciais — preenchem lacunas reais do plugin sem ferir guardrails. O restante deve ser rejeitado, rebaixado a complemento Java-only, ou refatorado pelo mantenedor do repo corp antes de qualquer integração. Mais grave: o build Gradle replica cada *.instructions.md em três formatos (instructions + SKILL + prompt), triplicando o conteúdo carregado pelo Copilot e duplicando princípios que o plugin já enuncia com mais rigor em speckit-baseline.

§ 1 · Conflitos diretos

Corp contradiz guardrail do plugin

Itens em que adotar a regra do repositório corporativo violaria diretamente um guardrail ativo do plugin. Nove ocorrências classificadas. Cada uma exige rejeição, rebaixamento de escopo ou isolamento em namespace Java-only.

# Item corp Guardrail do plugin que conflita Decisão
C1 copilot-instructions.md corp impõe "Always use the latest versions of dependencies" GitWorkflowGenerator + práticas de versionamento (SemVer, lock files, supply chain) Rejeitar no namespace global; manter apenas em skill corp-* se aplicável a projeto Java específico
C2 "Always write Java code as the Spring Boot application" + "Always use Gradle" + "com.grupopan group ID" + "Generate Docker Compose" no copilot-instructions.md global Plugin é multi-stack (TS/JS/Python/C#/Java) e detecta stack via Story Rejeitar como global. Mover para skill corp-java-spring com applyTo: "**/*.java"
C3 Self-Improvement Loop com tasks/lessons.md Plugin tem workflow story-driven com .speckit/; tasks/lessons.md não existe e contradiz a estrutura Rejeitar. Conceito incompatível
C4 metrics-observability: PanLogger como única forma aceita ObservabilityGenerator: OTel, traceparent W3C, logs JSON estruturados agnósticos Rebaixar a "complemento Java". Não pode ser global. Manter como adendo em skill corp-java-spring com aviso "padrão local Pan, não substitui baseline OTel"
C5 global-git-commit-instructions impõe gitmoji em PT-BR GitWorkflowGenerator: Conventional Commits puro (<tipo>(<escopo>): desc); compatível com commitlint padrão Rejeitar gitmoji obrigatório. Quebra hooks/CI padrão. Manter apenas tradução PT-BR opcional
C6 usecase-service-class: "explicit local try/catch em todo endpoint" SpringBootGenerator: @ControllerAdvice global Conflito ativo — escolher um padrão. Recomendação: manter @ControllerAdvice (plugin) e relegar try/catch local a casos excepcionais
C7 copilot-instructions.md corp instalado global em ~/.copilot/instructions/ e ~/.config/github-copilot/intellij/… Plugin opera em <workspace>/.github/ (VS Code chat participant) Escopo errado. Global JetBrains não se aplica; instalação global em ~/.copilot/ colide silenciosamente com config do workspace
C8 Frontmatter applyTo divergente: corp usa arrays Java-only; plugin usa "**" para baseline Misturar formatos quebra resolução do Copilot Normalizar: tudo do corp deve ter applyTo restrito à linguagem alvo
C9 Agente refinador-tarefas declara tools de escrita (apply_patch, insert_edit_into_file, create_file, run_in_terminal) Plugin restringe ferramentas por modo (debugger/refactor/implementador/revisor) e por gate da story Rejeitar como agente novo. Conceito já existe via custom agent engenheiro-senior e StoryImplementadorAgentGenerator
Padrão observado: os conflitos não são acidentais — refletem uma premissa arquitetural diferente: o corp assume um stack único (Java/Spring/Gradle/AWS) e instala regras como globais. O plugin assume multi-stack, derivação por Story e separação rígida entre baseline universal e camadas específicas. Sem isolar o corp em namespace, qualquer regra global dele quebra o contrato.
§ 2 · Sobreposições

Plugin já cobre, com mais profundidade

Conteúdo do corp que o plugin já endereça, em geral com mais rigor, mais profundidade ou nomenclatura multi-stack. Manter ambos cria competição entre fontes de verdade e infla contexto.

# Item corp Cobertura equivalente no plugin Veredicto
S1 Seções "Plan Mode Default", "Verification Before Done", "Demand Elegance", "Core Principles" (duplicadas em java.instructions.md) AgentIntegrityGenerator, TestingStandardsGenerator, ArchitectureGenerator (mais rigorosos: gate inegociável, CRAP score, testes comportamentais primários) Descartar do corp. Plugin é estritamente mais forte
S2 java.instructions.md (boas práticas básicas: constructor injection, Optional, Records) JavaGenerator (Java 17/21: virtual threads, sealed, pattern matching, SequencedCollection, StructuredTaskScope, text blocks) Descartar do corp. Plugin tem ~3× mais profundidade
S3 kafka-listener-resilience + kafka-producer-consumer-config KafkaGenerator (idempotência, DLT com headers, semântica at-least-once, schema registry, retry com jitter) Sobreposição alta. Manter do corp apenas trechos Spring-specific (@KafkaListener config, @RetryableTopic) como complemento
S4 feature-creation SKILL (workflow TDD 8 passos) Gates do plugin (Gate 1→2→3→4) + StoryUnifiedAgentGenerator + BaselineSkillGenerator (TDD + CRAP) Conceitualmente redundante. Plugin já orquestra esse fluxo via gates; manter levaria a dois fluxos paralelos competindo
S5 Agente refinador-tarefas (entrevista técnica, discovery) Custom agent engenheiro-senior + StoryImplementadorAgentGenerator Sobreposto. Ver também C9
S6 spring-rest-controllers (REST conventions: /api/v{n}, ResponseEntity, DTOs) SpringBootGenerator cobre camadas/JPA/configuração — não detalha REST controllers Lacuna útil do plugin. Uma das poucas peças do corp que agrega valor sem conflitar
S7 database-integration (JPA, @CreatedAt/@UpdatedAt, N+1, optimistic locking) SpringBootGenerator (JPA básico + paginação) Sobreposição parcial. Trechos sobre auditoria, N+1, @EntityGraph são complementares
S8 general-integration + http-integration (Gateway pattern + RestTemplate/WebClient/OpenFeign + Resilience4j) BffPatternGenerator, SpringBootGenerator (parcial) Sobreposição parcial. Resilience4j + Gateway naming úteis como complemento
S9 usecase-service-class (single responsibility, no framework leakage, constructor injection, custom exceptions) ArchitectureGenerator (hexagonal/clean) + feature-creation competindo Princípios já cobertos. Manter do corp apenas: nomenclatura *UseCase/*Gateway e estrutura de pacotes
§ 3 · Incoerências internas

Problemas do corp independentemente do plugin

Inconsistências do próprio repositório corporativo, que existem mesmo sem considerar o plugin. Devem ser sinalizadas ao mantenedor antes de qualquer integração.

# Problema Impacto
I1 copilot-instructions.md e java.instructions.md duplicam literalmente "Plan Mode Default", "Self-Improvement Loop", "Verification Before Done", "Demand Elegance", "Core Principles" Mesmo conteúdo carregado 2× pelo Copilot → desperdício de contexto
I2 Build Gradle gera 3 formatos (*.instructions.md + SKILL.md + *.prompt.md) para cada arquivo de instructions/ Triplica tokens carregados; mesma regra aparece como instrução always-on, skill on-demand e prompt reutilizável simultaneamente
I3 "Always use native language (e.g., Portuguese)" repetido em 3 lugares (copilot-instructions, java.instructions, feature-creation SKILL) Redundância pura
I4 feature-creation SKILL incorpora trechos do "ask for inputs" do copilot-instructions Acoplamento textual — manutenção quebra silenciosamente
I5 usecase-service-class lista "Related Customizations to Consider" com 7 bullets que são regras disfarçadas (custom exceptions, mapeamento HTTP, logging, wrapping de gateway) Regras importantes escondidas em seção "considerar" — Copilot pode ignorá-las
I6 Frontmatter incompleto: feature-creation não tem applyTo; refinador-tarefas declara argument-hint: "The inputs this agent expects, e.g., ..." (template não preenchido) Frontmatter inconsistente reduz precisão de roteamento do Copilot
I7 global-git-commit-instructions.md mistura instruções de commit message com code review (linhas 47-61 são prompt de review) Arquivo com duas responsabilidades; difícil manter
§ 4 · Itens complementares

O que do corp agrega valor sem conflitar

Estes oito itens preenchem lacunas reais do plugin sem tocar em guardrails universais. São o núcleo aproveitável do bundle corporativo.

A1 · AWS

aws-secrets-retrieval

SecretCache, @JsonAlias, CredentialsException. Plugin tem AwsGenerator (DynamoDB/RDS) mas não cobre Secrets Manager.

A2 · Persistência

mongo-connection

Plugin não cobre MongoDB. Convenções de @Document, pool, índices, tratamento de exceções.

A3 · Mensageria

rabbitmq-* (listener + config)

Plugin cobre apenas Kafka. RabbitMQ tem semântica distinta (DLX, CachingConnectionFactory, Declarables).

A4 · Scheduling

spring-scheduled-tasks

ShedLock para cluster, idempotência, métricas de execução. Plugin não cobre jobs agendados.

A5 · Spring

spring-config-beans

Convenções @Configuration, @ConfigurationProperties, descritor de beans. Sem equivalente no plugin.

A6 · REST

spring-rest-controllers

Versionamento /api/v{n}, ResponseEntity, @ControllerAdvice. SpringBootGenerator não detalha controllers.

A7 · AWS

aws-integration

AwsCredentialsProvider com WebIdentityTokenFile + Default. Específico de runtime AWS — complementa, não substitui.

A8 · Naming

usecase-service-class (parcial)

Convenções de nomenclatura *UseCase/*Gateway + estrutura de pacotes corporativa. Baixo risco.

Condição para aceitar A1–A8: viver isoladas em namespace corp-* com applyTo restrito (Java/Spring), nunca tocar em arquivos speckit-*, nunca ser carregadas always-on.
§ 5 · Eficiência de tokens

O custo invisível da adoção crua

O plugin foi desenhado com economia de contexto como guardrail. O bundle corp viola essa economia em três frentes simultâneas: duplicação literal entre arquivos, wrapping triplo do build, e proliferação de skills always-on.

Métrica Repo corp Plugin Comentário
copilot-instructions.md baseline (sempre carregado) ~3 KB (corp) + duplicação em cada instructions ~400 tokens (apenas índice) Plugin é ~10× mais econômico no always-on
Multiplicação por wrapping triplo 3× cada arquivo 1× Adoção direta do build corp triplicaria contexto
Sobreposição literal entre arquivos ~30% do conteúdo (princípios repetidos) ~0% (geradores compõem sem duplicar via stripFrontmatter) Plugin já elimina duplicação ao compor speckit-baseline
Skills always-on (descrição ativa por keyword) Todos os instructions viram skill ⇒ múltiplas always-on 1 baseline + 1 stack + 1 context (3 fixos) Carregamento simultâneo de N skills corp polui o contexto
Conclusão quantitativa: instalar o build corp como-está faz com que ~17 skills fiquem disponíveis simultaneamente ao Copilot, todas duplicando princípios já presentes no speckit-baseline. Aumento estimado de contexto: 5 a 8 vezes. Isso comprime a janela útil para o código do usuário e degrada a qualidade das respostas.

§ 7 · Princípios invariantes

Sete regras para qualquer futura integração

Estes princípios garantem que, qualquer que seja o mecanismo de distribuição conjunta adotado (Git, API, artifact, VSIX), os guardrails do plugin permaneçam intactos e a eficiência de tokens seja preservada.

P1

Namespace por prefixo

corp-* vs speckit-* — invariante de separação física. Elimina merge de conteúdo Markdown (frágil) substituindo por composição de catálogo.

P2

speckit-* é read-only

O instalador corp recebe deny-list explícita. Qualquer tentativa de escrita em speckit-* aborta a operação.

P3

Sem wrapping triplo

Um único formato por arquivo. Preferência: SKILL on-demand para conteúdo de stack; instructions only para regras de path.

P4

Princípios universais

TDD, plan-mode, verification, agent integrity, observability baseline só vivem em speckit-baseline. Corp não pode redefini-los.

P5

copilot-instructions.md

Continua sendo gerado exclusivamente pelo plugin; corp não escreve neste arquivo. Pode entregar um manifesto para o plugin referenciar suas skills.

P6

Hash + snapshot test

Templates speckit-* têm hash interno; snapshot tests em vitest detectam adulteração inadvertida.

P7

Frontmatter padronizado

Todo arquivo carrega source: corp|plugin-static|plugin-derived, bundleVersion, contentHash, generatedAt, pluginVersion.

Próximos passos sugeridos (fora do escopo deste inventário)

  • Levar este relatório ao mantenedor do data--copilot-guidelines para refatoração (resolver I1–I7).
  • Quando saneado, planejar o BundleManager no plugin (referenciado na análise anterior sobre distribuição conjunta).
  • Adicionar snapshot tests dos speckit-baseline* para defesa imediata, independente do bundle.

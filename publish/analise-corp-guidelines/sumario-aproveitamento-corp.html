§ 1 · Contexto para a leitura

Três premissas que orientam toda decisão

Antes de listar o que entra e o que não entra, é útil alinhar três premissas estruturais do plugin SpecKit. Elas explicam por que determinadas regras do repositório corp não podem ser adotadas no namespace global, e por que a integração acontece via skills corp-* on-demand.

Premissa 1

Camada universal multi-stack

O plugin atende projetos em TypeScript, JavaScript, Python, C# e Java. Regras escritas como globais que pressupõem stack específico (Java + Spring + Gradle + AWS) não podem viver no namespace global sem quebrar projetos de outras linguagens.

Premissa 2

Geração derivada por Story

Artefatos do plugin são gerados por workspace (em <workspace>/.github/), a partir da Story ativa e da stack detectada. Não há diretório global escrito pelo plugin no perfil do usuário. Diferença de escopo estrutural.

Premissa 3

Eficiência de contexto é guardrail

Cada token consumido pelo prompt-system é um token a menos para o código do usuário. Por isso o plugin mantém o copilot-instructions.md always-on em ~400 tokens e organiza skills em três camadas (baseline + stack + context).

§ 2 · O que aproveitamos

Treze contribuições, em sua maioria multi-stack

Os itens abaixo são integrados como skills corp-* carregadas on-demand. O applyTo de cada skill é definido pelo escopo técnico real do conteúdo: apenas três arquivos são intrinsecamente Spring e ficam restritos a Java; os demais valem para qualquer projeto que use a tecnologia correspondente (AWS, MongoDB, AMQP/RabbitMQ, Kafka, HTTP, padrões de naming/data access) independente da linguagem.

Itens Java/Spring específicos (3) — applyTo: "**/*.java"

Item corp Skill resultante Justificativa
spring-scheduled-tasks.instructions.md corp-spring-scheduled Anotações @Scheduled e padrão ShedLock para cluster são intrinsecamente Spring; sem equivalente fora do framework.
spring-config-beans.instructions.md corp-spring-config @Configuration, @Bean e @ConfigurationProperties são API Spring; sem equivalente conceitual em outras stacks.
spring-rest-controllers.instructions.md corp-spring-rest @RestController, ResponseEntity, @ControllerAdvice e versionamento /api/v{n} em Spring MVC.

§ 3 · O que não absorvemos

Quatro grupos de incompatibilidade arquitetural

Os itens abaixo ficam fora do plugin por motivos de escopo, sobreposição com guardrails universais ou geometria de carga de contexto. Cada grupo recebe um tratamento explícito.

Grupo A

Conflitam com a natureza multi-stack do plugin

Regras escritas como globais no copilot-instructions.md do corp pressupõem Java/Spring/Gradle/com.grupopan/Docker Compose. São válidas para projetos corporativos Java, mas inaplicáveis fora desse contexto. O plugin atende TS/JS/Python/C#/Java; aplicar essas regras como globais quebraria projetos das demais linguagens.

Tratamento: conteúdo movido para skill corp-java-spring com applyTo: "**/*.java". As regras continuam efetivas para projetos Java, apenas não são globais.

Grupo B

Escopo de instalação diferente

O instalador Gradle entrega arquivos em ~/.copilot/instructions/ e ~/.config/github-copilot/intellij/global-copilot-instructions.md (global do usuário). O plugin opera em <workspace>/.github/ (chat participant do VS Code, por workspace).

Tratamento: são canais diferentes que continuam coexistindo no ambiente do desenvolvedor. Não há colisão de funcionalidade, apenas escopos distintos.

Grupo C

Sobreposição com guardrails universais do plugin

Estes itens existem em ambos os lados; o plugin mantém a versão própria por motivos de cobertura multi-stack e rigor adicional. Manter os dois resultaria em conteúdo duplicado carregado pelo Copilot.

Item corp Motivo de manter a versão do plugin
Seções "Plan Mode", "Verification Before Done", "Demand Elegance", "Core Principles" Equivalentes em AgentIntegrityGenerator, TestingStandardsGenerator, ArchitectureGenerator com gate inegociável e CRAP score formalizado.
java.instructions.md JavaGenerator cobre Java 17/21 (virtual threads, sealed, pattern matching, SequencedCollection, StructuredTaskScope, text blocks). É superset técnico do conteúdo corp.
metrics-observability com PanLogger ObservabilityGenerator é agnóstico (OTel, traceparent W3C). PanLogger é mantido como complemento em corp-java-spring, não como substituto do baseline.
global-git-commit-instructions com gitmoji GitWorkflowGenerator usa Conventional Commits puros, compatíveis com commitlint padrão e hooks de CI. Localização PT-BR é preservada.
feature-creation SKILL (workflow 8 passos) Equivalente aos gates 1→2→3→4 do plugin, orquestrados pelo StoryUnifiedAgentGenerator. Manter ambos cria dois fluxos competindo.
refinador-tarefas agent Coberto pelo custom agent engenheiro-senior e StoryImplementadorAgentGenerator. Além disso, o agente corp declara tools de escrita amplas (apply_patch, run_in_terminal) — o plugin restringe ferramentas por modo e por gate como contrato de segurança.
usecase-service-class (princípios universais) Single responsibility, no framework leakage, constructor injection, custom exceptions já cobertos pelo ArchitectureGenerator. Convenções locais (naming, packages) são aproveitadas — ver §2.
usecase-service-class: "try/catch local em todo endpoint" Conflita com @ControllerAdvice global, padrão recomendado pelo SpringBootGenerator. Decisão técnica: manter @ControllerAdvice e relegar try/catch local a casos justificados.
Grupo D

Aspectos do build Gradle que multiplicam contexto

Wrapping triplo: cada *.instructions.md vira simultaneamente instructions + SKILL + prompt. O plugin adota apenas o formato adequado por arquivo (SKILL on-demand para conteúdo de stack; instructions para regras de path). Resultado: ~3× menos tokens carregados.

Múltiplas skills always-on: instructions com description ampla viram skills ativas por keyword simultaneamente. O plugin mantém apenas 3 always-on (speckit-baseline, speckit-stack, speckit-context-STORY-<id>); demais são on-demand.

§ 4 · Sugestões para o repositório

Pontos que tornariam o repositório mais útil em qualquer cenário

Observações independentes da integração com o plugin. Tornariam o repositório mais robusto para qualquer consumidor — humano ou automatizado.

S1 · Duplicação

Consolidar princípios duplicados

copilot-instructions.md e java.instructions.md repetem literalmente "Plan Mode", "Self-Improvement Loop", "Verification Before Done", "Demand Elegance", "Core Principles". Consolidar em um único arquivo evita inconsistência futura.

S2 · Build

Tornar wrapping triplo opcional

Permitir que cada *.instructions.md declare no frontmatter quais formatos quer gerar (apenas SKILL, apenas instruction, ou ambos). Reduz 3× o contexto carregado em consumidores que aproveitam o repo.

S3 · Acoplamento

Desacoplar feature-creation SKILL

O arquivo incorpora trechos copiados do copilot-instructions.md (seção "ask for inputs"). Desacoplar evita quebras silenciosas quando o copilot-instructions for alterado.

S4 · Visibilidade

Promover "Related Customizations"

No usecase-service-class, os 7 bullets sob "Related Customizations to Consider" são regras importantes disfarçadas (custom exceptions, mapeamento HTTP, logging, wrapping de gateway). Promover a regras explícitas aumenta a chance de o Copilot honrá-las.

S5 · Frontmatter

Padronizar frontmatter

feature-creation está sem applyTo. refinador-tarefas declara argument-hint com texto de template não preenchido. Pequenas correções que melhoram o roteamento do Copilot.

S6 · Coesão

Separar commit e code review

global-git-commit-instructions.md mistura convenção de commit (linhas 1-46) com prompt de code review (linhas 47-61). São duas responsabilidades; separar em dois arquivos facilita a manutenção.

Estas seis sugestões correspondem às incoerências internas I1–I7 mapeadas na análise técnica detalhada e são independentes da integração com o plugin SpecKit.
§ 5 · Próximo passo técnico

Alinhar o schema do manifesto de distribuição

A integração entre o instalador Gradle do repositório e o plugin SpecKit precisa de um contrato técnico explícito. Esse contrato é o manifesto de bundle entregue pelo instalador e consumido pelo plugin.

Campo 1

bundleVersion

Versão semântica do conjunto entregue. Habilita a comparação no plugin e a decisão de atualizar ou não.

Campo 2

Lista de arquivos por skill

Caminho relativo, skill de destino (corp-*) e applyTo resultante. Define o que entra em cada namespace.

Campo 3

contentHash SHA-256

Hash por arquivo para detecção de drift e validação de integridade no momento do install.

Campo 4 (opcional)

Assinatura do manifesto

Garante autenticidade da origem corporativa. Recomendado para o canal de distribuição em produção.

Definido o schema do manifesto, a integração passa a operar de forma reproduzível: o plugin consegue verificar versão, validar integridade e exibir ao usuário o status do bundle corp-* em uso.

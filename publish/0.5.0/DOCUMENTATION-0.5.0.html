Capítulo I · Visão da release

O que muda — e o que continua valendo

Nada do fluxo SDD foi reinventado. As cinco gates, os atores (User, Participant, LLM), a camada de prompts e os comandos existentes em 0.4.0 permanecem. A 0.5.0 adiciona seis instrumentos paralelos que tornam o pipeline mais seguro, mais transparente e mais resistente a falhas.

Quality-of-life

Detecção de segredos

Validador novo (SecretLeakValidator) executa nas transições de gate 2 e 3 e em /verify. Reconhece AWS, GitHub, JWT, PEM, Slack, Google e padrões genéricos. Placeholders óbvios são ignorados.

Observabilidade

Métricas locais

MetricsRecorder persiste cada execução em .speckit/metrics/events.jsonl com cap rotativo de 2 MiB. Comando /metrics resume p95, pass rate e top validators.

Spec quality

Score de spec

SpecCompletenessScorer calcula nota 0..100 em 7 dimensões. Sem LLM, roda em milissegundos. Comando /score mostra breakdown e recomendações concretas.

Loop inteligente

Revisor com memória

O prompt do Revisor passa a incluir tentativa atual vs limite, lista de validadores regredidos e validadores resolvidos. Acaba o "pedir a mesma correção de novo".

Robustez

Timeout por validador

ValidationRegistry aceita timeoutMs por execução. Em estouro, aborta via AbortController e emite finding sintético — sem travar o pipeline.

UX nativa

Status Bar + Problems

Item esquerdo do status bar mostra spec/gate/status. Painel Problems do VS Code recebe os findings da última evidência, navegáveis por arquivo:linha.

Capítulo II · Detecção de segredos

SecretLeakValidator — oito olhos no diff

O validador analisa arquivos tocados pela story (descontando node_modules, dist e arquivos de teste) e produz finding error quando reconhece padrões conhecidos de credenciais. A regex final foi calibrada com o caso de teste padrão do SDK da AWS (AKIAIOSFODNN7EXAMPLE) para evitar falsos positivos em material didático.

Capítulo III · Métricas locais

MetricsRecorder e o comando /metrics

Toda execução do pipeline (gate-verification, verify-command, spec-heuristic, incremental-crap) grava uma linha JSONL em .speckit/metrics/events.jsonl. O arquivo tem cap rotativo de 2 MiB: ao ultrapassar, as linhas mais antigas são descartadas. Nenhum dado sai da máquina.

Anatomia de um evento

{
  "ts": "2026-05-13T20:00:00.000Z",
  "type": "gate-verification",
  "specId": "S-014",
  "gate": 3,
  "passed": false,
  "durationMs": 1284,
  "validators": ["heuristic","secret-leak","crap","coverage"],
  "blockingCount": 2
}

O que /metrics resume

Pass rate

Percentual de execuções com passed=true.

p95 de duração

95º percentil de durationMs, indicador de cauda.

Top validators

Validadores mais executados por frequência.

By gate / by spec

Distribuição de execuções por gate e por story.

Capítulo IV · Score de spec

SpecCompletenessScorer — 0..100 sem LLM

Função pura scoreStory(story) percorre sete dimensões com pesos pré-definidos. Retorna score numérico, nível qualitativo (baixa, média, alta, excelente), breakdown por dimensão e recomendações concretas para subir o score.

Capítulo V · Revisor com memória

IterationContext — o loop que aprende

Em 0.4.0 o loop Revisor↔Implementador tinha um contador interno mas não expunha histórico ao agente. Na 0.5.0 o GateVerificationHook lê a evidência anterior do mesmo (spec, gate), calcula delta (regredidos vs resolvidos) e injeta um IterationContext no prompt enviado ao Revisor.

Conteúdo do IterationContext

interface IterationContext {
  attempt: number;          // tentativa atual (1..N)
  limit: number;            // 5 por padrão
  regressed: string[];      // validadores que voltaram a falhar
  resolved: string[];       // validadores que foram corrigidos
  limitReached: boolean;    // true quando attempt === limit
}

Fluxo de iteração

sequenceDiagram
    participant U as User
    participant P as Participant
    participant R as Revisor (LLM)
    participant I as Implementador (LLM)
    participant H as GateVerificationHook
    U->>P: /review-auto
    P->>H: collect(gate N)
    H->>H: lê evidência anterior
    H->>H: calcula delta
    H->>R: prompt + IterationContext
    R-->>I: instruções específicas
+ atenção a regressões
    I-->>H: código corrigido
    H->>H: re-run validadores
    alt passed
        H->>U: ✓ avança gate
    else attempt < limit
        H->>R: nova iteração com delta
    else attempt === limit
        H->>U: ✗ LIMITE ATINGIDO
    end
Limite: mantido em 5 por (spec, gate). Ao atingir, o prompt traz LIMITE ATINGIDO e o pipeline pára de tentar para evitar loop infinito.
Capítulo VI · Robustez · timeout por validador

ValidationRegistry com AbortController

Validadores externos (test-execution, coverage) podem demorar — ou pendurar — em monorepos grandes, redes lentas ou arquivos patológicos. O registry agora aceita timeoutMs por execução, encapsula cada validator num Promise.race e cancela via AbortController quando o limite é atingido, emitindo um finding sintético em vez de travar.

Sequência de cancelamento

sequenceDiagram
    participant Reg as ValidationRegistry
    participant Local as localAbort (AbortController)
    participant V as Validator.run()
    participant T as Timer
    Reg->>Local: new AbortController()
    Reg->>V: run({ signal })
    Reg->>T: setTimeout(timeoutMs)
    alt validator termina antes do timer
        V-->>Reg: Finding[]
        Reg->>T: clearTimeout
    else timer dispara primeiro
        T-->>Local: abort()
        Local-->>V: signal.aborted
        Reg->>Reg: emite Finding{severity: error,
msg: "excedeu timeout de Xms"}
        Reg->>Reg: marca perValidator com error="timeout"
    end
                    
// Uso típico:
await collector.collect({
  story, gate: 3,
  timeoutMs: 30_000   // novo em 0.5.0
});
Compatibilidade: parâmetro opcional. Quando ausente, comportamento idêntico a 0.4.0 (sem timeout).
Capítulo VII · UI nativa do VS Code

Status Bar e painel Problems

Duas superfícies pequenas, mas com alto retorno de UX: o status bar mantém visível a story ativa e o status da última validação; o painel Problems vira ponto de entrada para os findings com navegação clicável até arquivo:linha. Tudo se atualiza no save.

SpeckitStatusBar

  • Alinhamento: esquerda, priority 50.
  • Conteúdo: spec/gate/status (✓ ou ✗ N).
  • Clique: dispara comando speckit.openMetrics que abre /metrics.
  • Refresh: onDidSaveTextDocument e ao avançar gate.

SpeckitDiagnostics

  • Fonte: arquivo mais recente em .speckit/evidence/*.json.
  • Mapeamento: Finding → vscode.Diagnostic com severity preservada e Range ajustado (1-based → 0-based).
  • Origem: speckit/<validator-id> aparece na coluna "Source".

Capítulo IX · Compatibilidade e impacto

O que muda para quem já usa 0.4.0

Nada que você usava deixa de funcionar. Os comandos novos (/metrics, /score) são adições. O SecretLeakValidator pode produzir findings novos se você já tivesse segredos hardcoded — exatamente o ponto. O Revisor passa a receber contexto adicional, mas o formato do prompt segue retrocompatível.

Loop Revisorcontador interno+ IterationContext exposto
Timeout de validator—opcional via timeoutMs
UI nativa—StatusBar + Problems

Redenenhumanenhuma
Falsos positivos do secret-leak: se algum match indesejado ocorrer, use placeholders explícitos (${ENV_VAR}, <your-key>, changeme) — a detecção os ignora por design.

Roadmap pós-0.5.0 (não incluído nesta release)

  • Integrações com runners externos (item 6 da proposta) — adiado.
  • Heurísticas assistidas por LLM para score (item 8) — adiado.
